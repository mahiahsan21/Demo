## B) Defects List

### **DEFECT-01**

- **Class.Method:** `ParkingSlot.isCompatible(VehicleType, LocalDateTime, LocalDateTime)`
- **Description:** `TRUCK` has no `case` entry in the `switch` statement inside `isCompatible()`. The switch falls through to `default: return false` for every slot type, making it impossible to book any TRUCK regardless of the slot. `TRUCK` is a valid `VehicleType` in the enum and must be handled per the system's vehicle type definitions.
- **Suggested Fix:** Add a `case TRUCK:` block inside the switch that returns `isAvailable(startTime, endTime)` for compatible slot types (e.g. LARGE), similar to how BUS is handled.

---

### **DEFECT-02**

- **Class.Method:** `ParkingSlot.isCompatible(VehicleType, LocalDateTime, LocalDateTime)`
- **Description:** The `case MICROCAR:` block is missing a `break` statement at the end. When the slot type is not COMPACT or REGULAR (the `if` condition is false), execution falls through directly into `default: return false` instead of exiting the case cleanly. This is a structural code quality defect that, while producing correct output for the current set of cases, will cause unintended behavior if additional cases are added after MICROCAR in the future.
- **Suggested Fix:** Add `break;` at the end of the `MICROCAR` case block, after the closing brace of the `if` statement.

---

### **DEFECT-03**

- **Class.Method:** `ParkingSlot.isAvailable(LocalDateTime, LocalDateTime)`
- **Description:** The `isAvailable()` method iterates over all bookings in the slot's list without filtering by booking status. This means `CANCELLED` bookings continue to block the time window permanently. According to the documented lifecycle, a cancelled booking should free the slot for future bookings during that window.
- **Suggested Fix:** Inside the `for` loop in `isAvailable()`, add a condition to skip bookings with `BookingStatus.CANCELLED` before performing the time overlap check.

---

### **DEFECT-04**

- **Class.Method:** `ParkingSystem.book(Vehicle, ParkingSlot, LocalDateTime, LocalDateTime)`
- **Description:** The booking object is added to the `bookings` list before `transferFunds()` is called to charge the vehicle. If the vehicle has insufficient funds, `transferFunds()` throws `InsufficientFundsException` — but the booking has already been inserted into the list. The booking then permanently remains in the system in an unpaid, corrupt state. Per documentation, a booking should only be stored after successful payment.
- **Suggested Fix:** Move `bookings.add(booking)` and `slot.getBookings().add(booking)` to after the `vehicle.getWallet().transferFunds(SYSTEM_WALLET, amount)` call succeeds. If payment throws, the booking is never added.

---

### **DEFECT-05**

- **Class.Method:** `ParkingSystem.cancelBooking(Booking)`
- **Description:** There is no status guard to prevent cancellation of an already `COMPLETED` booking. The documented lifecycle is `ACTIVE → COMPLETED` or `ACTIVE → CANCELLED` only. Calling `cancelBooking()` after `completeBooking()` causes a financial inconsistency: 80% of the amount was already transferred to the slot wallet on completion, leaving the system wallet with only 20%. The cancel attempt then tries to refund 90% from the system wallet, which throws `InsufficientFundsException` and crashes the operation.
- **Suggested Fix:** At the start of `cancelBooking()`, check if `booking.getBookingStatus() == BookingStatus.COMPLETED` and throw an `IllegalStateException` with a descriptive message if so.

---

### **DEFECT-06**

- **Class.Method:** `Wallet constructor / Wallet.addFunds`
- **Description:** The `Wallet(double balance)` constructor accepts any `double` value without validation, including negative numbers, `Double.POSITIVE_INFINITY`, and `Double.NaN`. All are invalid monetary values that should be rejected at construction time. Additionally, because `double` arithmetic is used throughout the class, floating point precision issues arise (e.g. `0.1 + 0.2` yields `0.30000000000000004` instead of `0.3`), making the class unsuitable for reliable monetary calculations.
- **Suggested Fix:** In the constructor, validate that the balance is a finite, non-NaN value greater than or equal to 0 — throw `InvalidAmountException` otherwise. Consider replacing `double` with `BigDecimal` for precision-safe monetary arithmetic.

---

### **DEFECT-07**

- **Class.Method:** `Wallet.transferFunds(Wallet, double)`
- **Description:** There is no null check on the destination `Wallet` parameter in `transferFunds()`. Passing `null` as the destination causes a `NullPointerException` thrown internally from `toWallet.addFunds(amount)` instead of a clean, descriptive error at the method's entry point.
- **Suggested Fix:** Add `if (toWallet == null) throw new IllegalArgumentException("Destination wallet cannot be null");` at the start of the `transferFunds()` method.

---

### **DEFECT-08**

- **Class.Method:** `Vehicle constructor`
- **Description:** The `Vehicle` constructor accepts `null` as a `Wallet` argument, `null` as a `VehicleType`, and negative or zero values as `vehicleId` — all without any validation. A null wallet causes a `NullPointerException` on the first call to `getBalance()`. A null vehicle type propagates silently and can cause `NullPointerException` in any downstream code that calls `getVehicleType()`. Negative or zero IDs undermine the integrity of vehicle identification.
